# Opsentra Log Ingestion Pipeline

This document explains how logs travel from infrastructure servers to the Opsentra dashboard.

Opsentra uses a **multi-stage log ingestion pipeline** designed to be scalable, fault-tolerant, and capable of handling high log throughput.

The pipeline integrates **AWS CloudWatch, Redis, MongoDB, and background workers** to process logs efficiently.

---

# Pipeline Overview

```

Server Logs
│
▼
Opsentra Agent
│
▼
CloudWatch Agent
│
▼
AWS CloudWatch Logs
│
▼
LogCollectorWorker
│
▼
Redis Queue
│
▼
DbInsertWorker
│
▼
MongoDB
│
▼
Opsentra Dashboard

```

Each stage in the pipeline has a specific responsibility to ensure reliable log ingestion and real-time monitoring.

---

# Stage 1 — Log Generation

Logs originate from servers running applications or services.

Common sources include:

### System Logs

```

/var/log/syslog
/var/log/messages
/var/log/auth.log

```

### Web Server Logs

```

/var/log/nginx/access.log
/var/log/nginx/error.log

```

### Container Logs

```

/var/lib/docker/containers/*/*-json.log

```

These logs are generated by the operating system, services, and containers running on the server.

---

# Stage 2 — Opsentra Agent

The **Opsentra Agent** installs and configures the AWS CloudWatch agent on the server.

Responsibilities:

- Install CloudWatch agent
- Configure log file collection
- Detect instance metadata
- Configure log group naming
- Start log forwarding

The agent ensures logs are automatically shipped to AWS CloudWatch.

---

# Stage 3 — CloudWatch Agent

The **Amazon CloudWatch Agent** monitors log files and forwards new log entries to AWS CloudWatch Logs.

Example configuration:

```

/opt/aws/amazon-cloudwatch-agent/etc/opsentra-cloudwatch-config.json

```

The configuration defines:

- log file paths
- log group names
- log stream names
- timestamp formats

Example log group naming convention:

```

opsentra-<workspace_id>-system
opsentra-<workspace_id>-nginx
opsentra-<workspace_id>-docker

```

---

# Stage 4 — AWS CloudWatch Logs

CloudWatch acts as the **primary log ingestion buffer**.

Advantages of using CloudWatch:

- highly reliable log storage
- automatic scaling
- durable log persistence
- integrated with AWS infrastructure

Opsentra does **not push logs directly** to its backend. Instead it **reads logs from CloudWatch**.

This approach ensures:

- logs are never lost
- AWS remains the source of truth
- ingestion failures do not cause data loss

---

# Stage 5 — LogCollectorWorker

The `LogCollectorWorker` is responsible for retrieving logs from CloudWatch.

Execution interval:

```

every 10 seconds

```

Responsibilities:

- assume IAM role via STS
- list CloudWatch log groups
- fetch new log events
- track ingestion cursors
- push events to Redis queue

Example flow:

```

CloudWatch API
│
▼
LogCollectorWorker
│
▼
Redis Queue

```

---

# Cursor-Based Log Fetching

To avoid duplicate log ingestion, Opsentra maintains **cursor state**.

Stored in:

```

LogGroupCursor collection

```

Fields:

```

workspaceId
logGroup
lastTimestamp

```

This ensures only **new log events** are processed during each polling cycle.

---

# Stage 6 — Redis Queue

Redis acts as a **buffer between ingestion and storage**.

Reasons Redis is used:

- decouples ingestion from database writes
- absorbs traffic spikes
- supports high throughput
- enables horizontal scaling

Queue structure:

```

RPUSH logs_queue
LPOP logs_queue

```

Workers read logs from Redis and process them asynchronously.

---

# Stage 7 — DbInsertWorker

The `DbInsertWorker` processes logs from the Redis queue.

Execution interval:

```

every 3 seconds

```

Responsibilities:

- consume Redis queue
- batch insert logs into MongoDB
- broadcast logs to WebSocket clients
- update recent logs cache

Batch writes dramatically improve database performance.

Example flow:

```

Redis Queue
│
▼
DbInsertWorker
│
▼
MongoDB

```

---

# Stage 8 — MongoDB Storage

MongoDB stores processed logs permanently.

Log schema:

```

workspaceId
instanceId
logGroup
message
level
timestamp

```

MongoDB is chosen because:

- flexible schema for logs
- high write throughput
- efficient indexing
- scalable clusters

---

# Stage 9 — Real-Time Log Delivery

Once logs are stored in MongoDB, they become available to the dashboard.

Two mechanisms deliver logs to the frontend.

---

## Polling

The frontend periodically fetches recent logs.

API endpoint:

```

GET /api/v1/logs/recent

```

---

## WebSocket Broadcast

Workers publish logs using Redis pub/sub.

Advantages:

- near real-time updates
- efficient delivery
- minimal polling overhead

---

# Log Level Detection

Opsentra automatically classifies logs into levels.

| Level | Detection |
|------|------|
| ERROR | error, fatal, exception |
| WARN | warn, deprecated |
| DEBUG | debug, trace |
| INFO | default |

This classification enables quick filtering in the dashboard.

---

# Reliability Strategy

Opsentra ensures log reliability through multiple safeguards.

### CloudWatch Persistence

CloudWatch stores logs independently from Opsentra.

### Redis Queue Buffer

Prevents ingestion bottlenecks.

### Cursor Tracking

Prevents duplicate ingestion.

### Worker Decoupling

Allows independent scaling of ingestion and storage.

---

# Scalability Design

The pipeline is designed for high-scale infrastructure environments.

Key scaling strategies:

### Horizontal Workers

Multiple workers can run simultaneously.

### Queue-Based Processing

Redis buffers ingestion spikes.

### Batch Database Writes

Reduces database overhead.

### Stateless API Servers

Backend can scale horizontally.
